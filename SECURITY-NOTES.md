# Security notes — captured Google API keys

Recorded: 2026-10-08. Status: repository remediation implemented; historical copies and alert classification remain owner follow-up.

The user reported a GitHub warning about Google API keys in
`docs/verification/u05-anonymous-live/sources/`. The investigation was strictly
read-only: no key values were displayed, no network or authenticated API requests
were made, and no captures, commits, or history were changed. This note records
the findings and proposed follow-up; it does not authorize history rewriting.

## Findings

The affected `.bin` files are full decoded HTTP response bodies downloaded from
Google Sheets, not credentials generated by this application. The capture
journals record `HTTP GET decoded response body`, gzip content encoding,
`HTTP 200`, and `text/html; charset=utf-8`. Thus the retained bytes are decoded
response bodies rather than compressed wire bytes.

Of the 22 U05 capture files, six contain Google API key patterns. Each contains
the same 19 distinct strings once each: 114 occurrences in total. The other
16 U05 captures contain no matches to the pattern `AIza[0-9A-Za-z_-]{35}`.
This count concerns pattern matches, not confirmed valid credentials.

The detected strings occur in Google page configuration fields, including
`ritz_firstparty_api_key`, `docs_apiary_client_key`, and
`homescreen_drive_client_key`. This supports their origin in third-party frontend
content. Cloud project ownership, validity, restrictions, and privileges were
not established. Public embedding alone does not establish that a key is harmless.
The exact GitHub alert and its detected value were not independently matched.

The same set of 19 strings occurs in 12 U07 captures under `u07-verification/`,
introduced with commit `691a30052b21be26581adc5636d23e23f28da08c`.
Any future cleanup must account for both evidence sets and their history.

## Creation path and application use

1. `regulatory-change-impact-brief/scripts/check_sources.py` invokes the default
   anonymous read adapters, creates a run, and writes the source-access report.
   Its output is required to be outside repository inputs/current outputs.
2. `scripts/rci/adapters/anonymous_sheets.py` retrieves initial HTML, discovers
   tabs and native cells, retrieves per-tab CSV, and performs a fresh final HTML
   read to check identity, revision, inventory, and cell consistency.
3. `scripts/rci/adapters/reads.py` obtains `response.content` and passes it,
   together with retrieval metadata, to the evidence store.
4. `scripts/rci/evidence.py` hashes and writes those bytes to
   `sources/<attempt-key>.bin`, with matching start/terminal journals.
5. The U05 verification record documents retention of the live evidence in
   `docs/verification/u05-anonymous-live/`; Git history confirms its inclusion.

Paths beginning with `scripts/` above are relative to
`regulatory-change-impact-brief/`.

No implementation use of these keys was found. Anonymous mode constructs an
HTTP source with no credential reference, uses HTML and public
`/gviz/tq?...&tqx=out:csv` routes, and does not add API keys or authorization.
The parser reads identity, revision, tabs, and native cells without executing
JavaScript. None of the 19 detected values was found in repository files outside
`.bin` captures. The separate authenticated Sheets adapter uses externally
supplied OAuth bearer tokens, not these embedded keys.

## Verification dependencies

The original HTML is required by the current independent verification path:

- `scripts/rci/adapters/readiness.py` validates the journal/body hashes,
  reparses HTML, compares discovery results with journal metadata, and checks
  CSV values against the native cells and complete tab inventory.
- `tests/runtime/test_u06.py` directly consumes the U05 evidence directory for
  normalization integration and actual-response replay tests.
- `tests/runtime/test_u07.py` loads the same U05 journals and bodies for replay.
- `docs/u05-source-access.md`, `docs/verification/u05.md`,
  `docs/verification/u06.md`, and `tests/fixtures/u06/README.md` describe the
  retained evidence and its handoff.

Deleting the affected HTML, retaining only CSV, or editing the bytes in place
would break current checks or remove their independently verified identity and
completeness basis. Adding ignore rules alone does not untrack existing files or
remove their contents from Git history.

An in-memory experiment replaced only the detected key strings with a fixed
redaction marker in each of the six U05 HTML responses. All six redacted bodies
contained no remaining matches and produced exactly the same parsed document
identity, revision, tab inventory, and native cells as the originals and their
journal metadata. No derivative files were written.

This demonstrates feasibility for sanitized replay fixtures. It does not prove
the full test suite against such fixtures, remove other potentially sensitive
content, or make redacted bytes interchangeable with original hash-bound evidence.

## Safest follow-up

1. Match the GitHub alert to the capture and confirm the classification without
   displaying or copying key values into reports. If a key instead belongs to
   the project's own Google Cloud account, revoke or rotate it first. Do not
   assume ownership or attempt to use these keys to determine validity.
2. Preserve the complete original U05 and U07 evidence bundles outside Git in
   controlled evidence storage, with unchanged bytes, journals, and hashes.
   Record a nonsecret manifest and the process for obtaining and verifying them.
3. Create explicitly labeled sanitized replay fixtures with their own hashes
   and a manifest linking them to original captures and documenting the
   transformation. Keep the original HTTP evidence and derivative test material
   distinct; do not describe sanitized bytes as untouched downloaded responses.
4. Update U06/U07 replay tests and fixture documentation to use sanitized
   fixtures. Preserve a separate, explicit verification path against the
   externally stored original evidence. Missing originals must produce a clear
   limitation rather than an unsupported verification PASS.
5. Before removing tracked originals, verify discovery equivalence, native
   cell/CSV agreement, normalization results, provenance, source completeness,
   and failure outcomes. Run the relevant U05/U06/U07 checks and focused G2
   verification. Preserve the unchanged CSV dictionary basis or explicitly
   reassess any basis changes.
6. Exclude raw live evidence from future commits and scan proposed commits,
   including `.bin` files. Scan sanitized derivatives for other sensitive data;
   the investigation here only counted one Google API key pattern.
7. Decide separately whether existing history needs purging. A cleanup commit
   leaves prior copies in history. Any rewrite requires explicit authorization,
   coordination with collaborators, and attention to branches, tags, and
   existing clones; it changes the recorded U05/U07 commit identities.
8. Resolve the GitHub alert with an accurate explanation only after confirming
   what it represents. Do not mark it revoked or used in tests solely because
   the string was included in verification evidence.

Do not overwrite original captures and update their hashes to conceal redaction.
Do not disable secret scanning for the evidence directories as a substitute for
classification and cleanup.

## Remediation implementation — 2026-10-08

See [secret safety and evidence replay](docs/secret-safety.md) for the implemented
controls, external original location, nonsecret manifest, reproduction commands
and remaining history/alert boundaries. All 19 GitHub alerts matched captured
keys; all were already resolved as `used_in_tests`, which does not establish
revocation or ownership. No alert resolution or Git history was changed.

Implemented guardrail: `scripts/secret_guard.py` uses Gitleaks default rules plus
Google API key/private-key header detection against staged blobs, including
binary content. Raw evidence and credential paths are rejected. The installed
Git hook preserves the existing Entire hooks. `docs/secret-safety.md` documents
per-clone installation and the narrowly scoped noncredential attempt-key exception.

The nonsecret fixture manifest covers 249 original files; 18 HTML bodies have
342 Google API key occurrences and 18 frontend token occurrences redacted.
Broad scanning of the proposed repository contents found no remaining findings.
External-original verification confirms original hashes, reproducible derivatives,
discovery/native-cell equivalence, CSV/dictionary basis, normalized values and
U07 source completeness/failure outcomes. Missing originals explicitly fail with
a limitation. Historical copies remain in Git until separately authorized cleanup.

Verification: 185 U05/U06/U07, G2 handoff and guardrail cases passed in the
combined run; 16 focused cases also passed after adding missing-scanner and
exception-scope coverage and updating the negative U05 fixture path. U01 frozen
inputs/structure and eight negative regressions passed. The explicit original
verifier passed; its missing-original case returned nonzero with LIMITATION.
The 249 checkout originals were removed only after these checks and another
byte/hash comparison with the controlled external copy.
